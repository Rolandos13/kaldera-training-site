Answer key — what's planted, and how to patch it

1. OSINT surface

Page source contains a code comment with a fake staging URL, placeholder API key, a leftover QA account, and a ticket reference. The Team section exposes a predictable email-naming pattern (f.lastname@domain), which in real assessments is exactly how you'd build a phishing/credential-stuffing target list.

Fix: never leave debug/TODO comments or credentials in shipped source; strip them in a build step. Avoid publishing a guessable email pattern alongside full staff names, or at least be aware of the exposure.

2. robots.txt-style hint

The team page mentions /staff-portal/ and /admin-legacy/ as "disallowed" — a classic case of robots.txt being used to hide paths instead of restrict crawling, which actually advertises them to anyone reading the file.

Fix: robots.txt is not access control. Sensitive paths need real authentication/authorization, not "security through obscurity."

3. Reflected XSS (Feedback wall)

User input is inserted with innerHTML without escaping, so HTML/JS in the message executes.

Fix: escape output (encode <, >, &, quotes) or use textContent/safe templating instead of raw HTML insertion; apply a Content-Security-Policy as defense in depth.

4. Naive login "SQL" bypass

The login check simulates building a query like user='x' AND pass='y' by string concatenation. Entering a username like ' OR '1'='1 makes the simulated check pass regardless of password — mirroring real SQL injection.

Fix: use parameterized queries / prepared statements, never concatenate user input into a query string; also enforce proper hashing for passwords and rate-limit login attempts.

Suggested exercise flow

1) Reconnaissance: read page source, find the comment, note the email pattern, note the "disallowed" paths.
2) Try the XSS payload in Feedback, observe execution, then rewrite the render function safely (this is a static page, so as a stretch task try patching the JS below to use textContent).
3) Work out the login bypass, then discuss/write what a parameterized query fix would look like in a real backend language (e.g. Python + psycopg2, or Node + pg).
